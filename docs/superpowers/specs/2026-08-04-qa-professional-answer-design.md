# 问答智能体气象专业化 — 回答结构 / 信息冗余 / 响应速度 设计

**日期**：2026-08-04
**状态**：设计（待用户审阅）
**范围**：`chainlitexam` 问答智能体（Chainlit 网页端）

## 背景与目标

甲方（气象预报老师）反馈问答智能体存在三类问题，要求"问答气象专业化"：

1. **回答结构**：思考过程与结论位置错位 → 希望**思考过程在上、回答（结论）在下**。
2. **信息冗余**：回答中包含与问题无关的明细（如问市台预警，表格仍列出全市各区县）。问题是多方面的，需排查并加通用规则。
3. **响应速度**：非简单查询响应慢（20s+），需优化结构瓶颈。

## 现状与根因

### 1. 回答结构 — 思考过程与结论位置错位

**根因**：`message_orchestrator.py` 的 `process_message` 主流程（约 4322-4326 行）：

```python
stream_msg = cl.Message(content="")     # 先创建回答消息
await stream_msg.send()                 # 先发送回答
reasoning = ReasoningStep("🤔 思考过程") # 后创建思考过程
await reasoning.__aenter__()            # 后发送思考过程
```

回答消息先行发送，思考过程后发送 → 网页端显示顺序为"回答在上、思考过程在下"。而 fast path 路径（`_emit_fast_path_result`）是先建思考过程、后发回答，顺序正确。**问题仅出在主流程**。

**附带**：`_prepend_thinking_summary`（28 处调用）在回答开头前置"思考摘要"（如"已结合实况数据完成分析，为您整理结论如下："）。思考过程置顶后，该摘要与思考过程存在语义重复，需评估精简。

### 2. 信息冗余

**根因**：`prompts.py` 已有大量反冗余规则（第 88、100-102、305、440 行等），但：
- **代码生成的表格**不受 prompt 规则约束，固定输出全部明细。典型：`tools/warning_workflow.py` 的 `finalize_warning_answer` 组装"核心结论 + 预警清单表格（含'影响区域'列）+ 预警内容 + 防范建议"，表格"影响区域"列固定列出所有区县，即使问市台预警。
- 其他代码生成表格（面雨量、河网、水位等）可能存在同类问题，需排查。

### 3. 响应速度

**根因**：`message_orchestrator.py` 的 `_run_tool_round`（约 1763 行起）用 `for` 循环**串行**执行 `planner_msg.tool_calls` 中的每个工具。若 planner 一轮发出多个工具调用，各工具查询延迟**累加**。多个相互独立的工具可并行执行，把串行延迟叠成一次。

## 设计

### 设计 1：回答结构 — 思考过程在上，回答在下

**目标**：网页端聊天中，"🤔 思考过程"步骤显示在回答消息**上方**。

**改动**：重排 `process_message` 主流程，先创建并发送 `ReasoningStep`，再创建并发送 `stream_msg`。具体顺序变为：

1. 创建并 `__aenter__` 进入 `ReasoningStep("🤔 思考过程")`（先发送）
2. 再创建 `stream_msg = cl.Message(content="")` 并 `send()`（后发送）
3. 后续推理阶段、关闭思考、流式回答逻辑不变

**约束**：
- 需保证 `stream_msg` 后创建但仍能正常流式承载回答（`stream_text_to_message` 依赖该对象）。
- 简单天气规则路由、THINKING_PLANNER 等不依赖先后顺序的逻辑保持原样。
- 思考过程关闭（`_maybe_close_reasoning`）时机不变——在发送最终答案前关闭。

**附带处理**：`_prepend_thinking_summary` 的"思考摘要"在思考过程置顶后语义重复，保留但**精简为简短业务引导语**（不重复"已分析/已查询"等与思考过程重复的内容），避免冗余。

**验收**：网页端聊天中，"🤔 思考过程"折叠步骤位于回答消息上方；思考过程自动折叠后回答清晰可见。

### 设计 2：信息冗余（双管齐下）

**目标**：回答只输出与用户问题直接相关的内容，不展开无关明细、区县、表格。

**① 通用 prompt 规则（`prompts.py`）**：
- 在回答规范区新增/强化一条强制规则：**只输出与当前问题直接相关的内容**；未问的区县明细、行政区划、时段、表格、风险建议不展开；可结构化的明细仅在用户明确要求时以表格呈现。
- 与现有第 100-102 行规则呼应，但改为更具体、更可执行的细则（给出"问市台预警不该给全市各区县"这类正反例）。

**② 代码表格裁剪（`tools/warning_workflow.py`）**：
- 预警表格按用户问法作用域裁剪"影响区域"列：
  - 问"市台/全市预警"等市级范围时，不展开各区县明细，只保留市级层面。
  - 问具体区县时，仅保留该区县相关记录。
- 排查其他代码生成表格（面雨量、河网、水位、决策天气等）的同类冗余，按问法作用域裁剪。

**验收**：问"市台有哪些预警"时，预警表格不列出全市各区县"影响区域"明细；其他回答不再输出与问题无关的区县/明细。

### 设计 3：响应速度 — 并行执行独立工具

**目标**：多工具查询的串行延迟叠成一次。

**改动**：`_run_tool_round` 中，将**相互独立**的工具调用改为 `asyncio.gather` 并行执行。

**并行化约束**：
- **只并行纯数据查询工具**（如 `get_city_rainfall_time_range`、`get_river_system_rainfall_forecast`、`query_current_weather_observation` 等，无全局副作用）。
- **有全局副作用的工具保持串行**：GIS 联动发送（`send_gis_linkage`）、图渲染（`render_and_send_plot`）、预警收口（`warning_bundles` 追加）、`forced_final_text` 赋值、`analyze_rainstorm_impact` 的分支处理。
- 并行工具的结果需按原顺序归并回 `messages`（ToolMessage 必须与 tool_call_id 对应），保证 LangChain 上下文正确。
- 需处理并行期间的异常隔离（单个工具失败不影响其他工具），并保留现有容错重试逻辑（`_invoke_tool_with_tolerance`）。

**验收**：planner 一轮发出多个数据查询工具时，总耗时从"各工具耗时之和"降为"最慢工具耗时 + 少量调度开销"。

## 风险与取舍

- **并行工具**：LangChain 消息顺序与工具副作用是主要风险，需严格隔离。若并行收益不明显或副作用复杂，可退回"仅对明确无副作用的工具并行"。
- **回答结构重排**：影响所有走主流程的查询，需回归验证各类型回答。
- **冗余裁剪**：通用规则可能误伤"领导想看完整清单"的场景，需保留"用户明确要求时给出完整表格"的出口。
